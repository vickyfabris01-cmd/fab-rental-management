Ground rules for every phase

  1. Every page opens, always. Nothing in a menu may lead to a blank screen or a 404. A screen that belongs to a later phase is registered with its phase number and opens a ComingSoon page that says which phase delivers it. The developer of that phase replaces the placeholder. Nothing else changes.
  2. A phase is finished when a person can test it in the browser. Each phase ships with seed data, demo accounts and a written test script. If a tester needs a developer to set something up by hand, the phase is not finished.
  3. One module per business type. Rental, agriculture and shop each live in src/modules/&lt;type&gt;/. A module registers its navigation, routes and dashboard in src/modules/registry.js. Modules never import from each other. Shared things live in src/components, src/lib and src/store.
  4. Same look, tokens only. Colours, sizes, spacing and motion come from src/styles/tokens.css. No hex values, no hard-coded pixel sizes for those things. Shared parts come from src/components/ui. Class prefixes: ui- for shared parts, shell- for the app frame, and a short module prefix for page styles (rent-, farm-, shop-).
  5. Every page handles four states. Loading (skeleton), empty (EmptyState with a next action), error (message and retry), and success. Phones first: usable at 375px, no sideways scrolling, 44px touch targets, text never below 12px, light, dark and system themes.
  6. No database calls inside components. Each domain has one data file in src/lib/data/ (for example rentalBuildings.js) that returns { data, error }. Pages call hooks that call those files. This keeps the screens easy to test and the queries easy to review.
  7. Database changes are migrations, not clicks. Every change is a numbered SQL file in supabase/migrations/ named pN_NN_description.sql, tested first on a Supabase branch, with row-level security on every table. Seed data goes in supabase/seed/pN.sql. Never edit a migration that an earlier phase delivered; add a new one.
  8. English only, plain words. All screen text is English, short and in the user's terms. Money is shown as KSh with thousands separators. Dates use d MMM yyyy. Phone numbers are stored as +2547XXXXXXXX.
  9. Header comment on every file. The first line is the file path and NEW or MODIFIED. A short AIM paragraph says what the file is for and how to use it. This is how many developers read each other's work.
  10. Rule no 1 stays. Before editing any file in the shared repository, check the local copy is on the latest commit. Phases that are handed over as a zip start from that zip, and the hand-off note names the commit it was built on.

Data model decisions

Changes to the existing Supabase project (fabrentals-dev). Every change is tested on a Supabase branch first.

  • The development database (fabrentals-dev) has 23 public tables and 6 migrations, all with row-level security on, and one edge function (create-admin-user). The tools report 0 rows in every table. That may be an estimate, so Phase 1 checks real counts before changing anything.
  • tenants becomes businesses. The table is renamed in place so ids and foreign keys are kept, and a view called tenants is left behind so old code keeps working until the old pages are deleted.
  • Exactly one owner per business. The existing migration allow_multiple_owners_and_visitor_or_owner_assign is reversed: businesses.owner_id is required, and a rule stops a second owner being added. Managers, workers and residents are rows in a new business_members table.
  • profiles.role and profiles.tenant_id are kept and filled by a trigger from business_members until Phase 3 has moved every rental screen to the new tables. Phase 3 then removes the trigger and the old columns.
  • Existing rental tables keep the column name tenant_id (it holds the business id). New tables use business_id. Renaming the old columns is optional hardening in Phase 5.
  • The existing tenant_secrets table holds per-business payment credentials. Its policies are tightened in Phase 1 so only the owner can write and nobody can read the values back from the browser.
  • Existing live data (the Sunrise and TULUMBA HOSTELS businesses, if present) is migrated in place as active rental businesses, with their current owners kept.

Build order and what can run in parallel

Phase 1 comes first because every other phase uses what it hands over. After that, Phases 2 and 4 can be built at the same time by two developers. Phase 3 needs the rental tables from Phase 2. Phase 5 needs the notification, message and ticket parts from Phase 3 and the chart and map parts from Phase 4.

Phase 4's report screens for rental are merged after Phase 2 is delivered. The rest of Phase 4 does not wait for it.

Database

  • p1_01_business_core: rename tenants to businesses (with the compatibility view). Add type (rental, agriculture, shop), status (draft, pending, active, rejected, suspended), owner_id (required), slug (unique), description, cover and logo, county, town, contact details, rejected_reason, approved_at, approved_by. Create business_members (business_id, user_id, role, status, invited_by) and the trigger that keeps profiles in step. Add profiles.global_role (user or super_admin). Reverse the multiple-owners migration.
  • p1_02_platform_settings: one settings row (product name, tagline, logo, support email, domain, currency, approval mode manual or automatic, maintenance mode, module switches for agriculture and shop, default commission percent stored only, M-Pesa mode sandbox or live). plans (business type, price in KSh, billing period, trial days, active). subscriptions (business, plan, status, period start and end).
  • p1_03_payments_core: payment_intents (purpose subscription, rent, order; business; payer; phone; amount; checkout and merchant request ids; status; receipt number; raw callback). One table for every M-Pesa payment in the product.
  • p1_04_notifications_core: adapt notifications (user, business, type, title, body, link, read time) and add the notify() function.
  • p1_05_audit_log: who did what, to what, when, with before and after values. Approvals and settings changes write here from Phase 1.
  • p1_06_storage_and_rls: storage buckets business-media (public read) and avatars; helper functions (is_super_admin, is_member, member_role, is_business_active); new policies for the identity tables; tightened tenant_secrets.
  • Public read: only active businesses are visible to the public, and only their public fields.

Functions and integrations

  • mpesa-stk-push, mpesa-callback, mpesa-status: Daraja STK Push in sandbox. Credentials are read from secrets. With no credentials set, the screen offers the super admin's manual "mark as paid" so testing is never blocked.
  • resolve-login: turns a phone number into the matching account so people can sign in with phone and password. No SMS is needed.
  • send-email: transactional email (approval, rejection). If no provider key is set it logs and returns success, so flows never fail because of mail.
  • Google sign-in: configured in the Supabase dashboard (client id and secret, redirect URLs). The setup steps are written in docs/phase-1/SETUP.md.
  • Existing create-admin-user function: reviewed and kept for creating the first super admin.

Acceptance test

A tester who has only the zip and the setup notes can do every step in the browser.

  1. Run npm install, copy .env.example to .env, run npm run dev. / loads and every link in the header, footer and menus opens a real page.
  2. Sign up with an email, confirm it, sign out, sign in. Sign in again with the phone number and password. Use Continue with Google on the staging site.
  3. Open /start. Rental can be chosen. Agriculture and Shop show "Coming soon".
  4. Fill in the business details and reach the subscription step. Pay with the M-Pesa sandbox. A successful payment moves the business to Pending approval. A cancelled payment shows a retry button.
  5. Sign in as the super admin. The new business is in /admin/businesses. Approve it. The owner gets an in-app notification and the business appears on /explore and at /b/:slug.
  6. Reject another business with a reason. The owner sees the reason on /start/status, edits and resubmits.
  7. In admin settings switch approval to automatic. A new business goes live without review.
  8. Change the product name and support email in admin settings. Both change in the header, footer, 404 page and avatar menu.
  9. Open /app/:slug/properties as the owner. A ComingSoon page names Phase 2.
  10. Switch light, dark and system themes. Check 375, 768 and 1280 pixel widths. No sideways scrolling and no console errors. npm run build passes.

Hand-off

bizkenia-phase-1.zip: the full project without node_modules or .env, plus docs/phase-1/ (README, SETUP, CONTRACTS, ACCEPTANCE, CHANGELOG), supabase/migrations, supabase/seed and supabase/functions. Demo accounts (all on example.com): super admin, a rental owner with an active business, a rental owner with a pending business, and a plain visitor.

Risks

  • Phone login without SMS is a choice (see decisions). Real one-time codes need an SMS provider and cost.
  • M-Pesa live credentials are needed only at launch. Sandbox is enough to finish and test this phase.
  • Google sign-in needs a Google Cloud project and consent screen. Until then the button shows but is switched off with a visible note.

Rental core for owners and managers

An owner or manager can run a rental business end to end: set up the property, receive and approve requests, bill residents and record payments.

Starts from the Phase 1 zip. Uses the shell, registry, permissions and mpesa.js unchanged.
